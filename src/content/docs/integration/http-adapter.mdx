`@loquix/adapter-http` builds an [`AgentProvider`](/docs/integration/agent-provider/) for you out of a URL. Point it at your own backend and it POSTs the conversation, reads the response as it streams in, and turns it into the plain-text `ReadableStream` the interface expects — including the abort handling, the non-2xx rejections, and the frame-by-frame decoding a hand-written provider would otherwise have to implement itself. It replaces the `send()` method on that page, not the interface: everything the agent controller expects from a provider still applies.

The package has zero runtime dependencies and holds no credentials. The URL it POSTs to is your own backend, so provider API keys stay on your server; see [keeping keys safe](/docs/integration/keeping-keys-safe/) for why that split exists and what it costs you to keep.

## Install

```bash
pnpm add @loquix/adapter-http
```

## A ten-minute example

```ts
import { createHttpAgentProvider } from '@loquix/adapter-http';

const provider = createHttpAgentProvider({
  url: '/api/chat',
});
```

Hand `provider` to `AgentController` the same way you would a hand-written one. By default the adapter POSTs `{ messages, model, params, systemPrompt }` to `/api/chat` and reads the response as server-sent events, extracting each frame's `data:` payload as plain text.

If your backend streams newline-delimited JSON objects instead, set the transport and nothing else changes:

```ts
const provider = createHttpAgentProvider({
  url: '/api/chat',
  transport: 'ndjson',
});
```

## Options

The table lists every field of `HttpAgentProviderOptions`, in the order the interface declares them.

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `url` | `string \| ((messages, options) => string)` | *(required)* | The endpoint to POST to. A function receives the outgoing messages and send options, so the URL can vary per request — for example to embed a conversation ID. |
| `name` | `string` | `'HTTP'` | The provider's `name`, used for logging and display, not routing. |
| `transport` | `'sse' \| 'ndjson' \| 'text'` | `'sse'` | Which wire format to decode the response as. See "Transports" below. |
| `headers` | `Record<string, string> \| (() => Record<string, string> \| Promise<Record<string, string>>)` | *(none)* | Extra request headers, merged over the adapter's own `content-type: application/json`. A function may be async, so a fresh auth token can be fetched per request. |
| `credentials` | `RequestCredentials` | `'same-origin'` | Passed straight through to `fetch`. |
| `body` | `(messages, options) => unknown` | posts `{ messages, model, params, systemPrompt }` | Overrides the JSON body sent to the endpoint. Whatever it returns is `JSON.stringify`'d as-is. |
| `parse` | `(chunk: string) => string \| null` | transport-dependent, see "Transports" | Overrides how a decoded chunk becomes text. See "The `parse` hook" below. |
| `fetch` | `typeof globalThis.fetch` | `globalThis.fetch` | Swap in a wrapped or polyfilled `fetch`, or a stub for tests. |

<Aside type="note">
`headers` is merged case-insensitively: the adapter lowercases every key you supply before merging it with its own `content-type` default, so a header you write as `Content-Type` overrides the adapter's default instead of sitting beside it as a second, distinct header.
</Aside>

## Transports

The `transport` option picks how the response body is decoded into text chunks. All three read the response as a stream of bytes; they differ in how they split it into frames and what, if anything, they parse out of each one.

### `sse` (default)

Expects [server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events): frames separated by a blank line (`\n\n`, or `\r\n\r\n`), each carrying one or more `data:` lines. Several `data:` lines in one frame are joined with `\n`; `event:`, `id:`, and comment (`:`-prefixed) lines are read and discarded. The default parser returns each frame's joined `data:` payload verbatim — no JSON parsing.

### `ndjson`

Expects one JSON object per line, separated by `\n`. The default parser reads `text`, `content`, or `delta` (in that order) off each parsed object and returns whichever is a string. A line that parses as JSON but carries none of those three fields is skipped — not an error, just no text to emit for that line.

### `text`

Expects nothing in particular. Every byte that arrives is decoded and passed straight through as a chunk of the output stream, with no framing and no parsing. Choose this when your backend already streams plain text and any structure — including a literal `[DONE]` — should reach the caller as ordinary bytes rather than being interpreted by the adapter.

<Aside type="caution">
A malformed line is handled differently depending on where it goes wrong. If a line arrives that the default `ndjson`/`sse` parser cannot make sense of — invalid JSON, or JSON with none of the expected fields — the adapter skips that one line and keeps streaming; a single hiccup on the wire does not fail the whole response. But if you supply your own `parse` and it throws, that exception is not caught: it propagates out of the stream, and whatever text had already accumulated in the response is lost. The asymmetry is deliberate. A bad line from the network is an expected condition the library can recover from; an exception from your own `parse` is a bug in your code, and swallowing it would hide that bug behind a silently truncated response instead of surfacing it.
</Aside>

## Errors

Every rejection from `send()` is an `HttpAgentError`, an `Error` subclass with a `status: number`:

```ts
class HttpAgentError extends Error {
  readonly status: number;
}
```

Two things reject with it:

- **A non-2xx response.** The adapter tries to read the body as JSON and use its `message` or `error` field as the error text; if the body isn't JSON, it falls back to the response's status text. Either way, `status` is the response's actual HTTP status.
- **A 2xx response with no body at all.** Some servers can return `200 OK` with an empty body — nothing to stream. The adapter treats this the same as a failure: it rejects with `HttpAgentError` and `status: 502`, since there is no real response to hand the controller.

A malformed *line inside* a body that did arrive is not one of these cases — see the caution above. Only a missing body, or a non-2xx status, fails `send()` itself.

## Cancellation

Cancellation flows in both directions between the returned stream and the underlying `fetch`:

- **Cancelling the stream cancels the response.** If the code consuming `response.stream` calls `reader.cancel()` (or the controller's own `abort()` does the equivalent), the adapter cancels the underlying response body too, so the connection doesn't keep receiving data nobody is reading.
- **Aborting the signal errors the stream.** The `signal` on `AgentSendOptions` is forwarded to `fetch`. If it aborts mid-response, the next read from `response.stream` rejects with a `DOMException` named `AbortError`, and the underlying body is cancelled.

`[DONE]` ends the stream the same way for `sse` and `ndjson`: as soon as either transport reads a frame or line whose payload is exactly `[DONE]`, it closes the output stream and cancels the underlying response body — even if the server keeps the connection open past that point. The `text` transport never does this: with no framing to interpret, a literal `[DONE]` in the byte stream is just more text, passed through like everything else.

## The `parse` hook

Set `parse` to replace the default per-transport parsing entirely. It receives one decoded chunk — one `sse` frame's joined `data:` payload, or one `ndjson` line — and returns the text to emit, or `null` to emit nothing for that chunk. It is never called for the `text` transport, which has no per-chunk parsing step to override.

The most common reason to supply one is a vendor API whose stream doesn't match the adapter's own `text`/`content`/`delta` convention. For an OpenAI-shaped SSE stream, where each frame is a JSON object with the token under `choices[0].delta.content`:

```ts
const provider = createHttpAgentProvider({
  url: '/api/chat',
  parse: chunk => {
    const parsed = JSON.parse(chunk);
    return parsed.choices[0]?.delta?.content ?? null;
  },
});
```

Given frames whose payloads are `{"choices":[{"delta":{"content":"Hel"}}]}` and `{"choices":[{"delta":{"content":"lo"}}]}`, this accumulates to `"Hello"`.

<Aside type="caution">
Write `parse` defensively. As covered under "Transports" above, an exception thrown out of `parse` is not caught — it errors the stream and discards whatever text had already accumulated, rather than being treated like a malformed line and skipped.
</Aside>

## Where this fits

`createHttpAgentProvider` returns an ordinary [`AgentProvider`](/docs/integration/agent-provider/) — hand it to `AgentController` and nothing downstream needs to know the send it drives is happening over HTTP at all. It exists so that connecting a backend that speaks SSE, NDJSON, or plain text doesn't require writing the stream-decoding half of a provider by hand; see the agent provider page if your backend needs something this adapter's options can't express, since a hand-written `send()` remains the fallback for anything more unusual.
